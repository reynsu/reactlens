# Interpolate the Detected stack into the Scaffold at init, not at runtime

`reactlens init` already infers a **Detected stack** (router, build tool, dev-server port, package manager, React version) via `detectStack`, but it copies the source templates into the user's project **verbatim** — `copyOne` is a plain `fs.copyFile`, and the detection result is only logged. The `playwright.config.ts` template therefore ships hardcoded `baseURL: 'http://localhost:5173'` and `webServer.command: 'pnpm dev'`, so a project is **Runnable** out of the box only on the reference stack (Vite + pnpm + port 5173). A Next.js App Router app (port 3000, `next dev`) or any npm/yarn project gets a Scaffold that does not match its stack and must be hand-edited — which is exactly the "additional configuration" we want to eliminate. `reactlens run` does not rescue this at runtime: it delegates the dev server to Playwright's `webServer` config and only injects `REACTLENS_*` behavioural env vars, never the server command or port.

**Decision:** `init` interpolates the Detected stack into the **Scaffold** at write time. The concrete dev-server port, the `<package-manager> run dev` command, and the test directory are baked into the generated `playwright.config.ts` (and the component globs into `reactlens.config.ts` — see consequences), rather than being deferred to runtime env injection by `reactlens run`. The `REACTLENS_BASE_URL` / `REACTLENS_WEB_SERVER` / `REACTLENS_NO_WEB_SERVER` env overrides remain as escape hatches, but they are no longer the only way to get a correct config.

**Why init-time over runtime.** The default `pattern: 'pom'` is documented (in `reactlens.config.ts` and ADR-0006) as producing **portable** specs that run under plain `npx playwright test` without reactlens driving the run. A runtime-injection design — where `reactlens run` calls `detectStack` and exports `REACTLENS_WEB_SERVER`/`REACTLENS_BASE_URL` on the fly — would leave the user's `playwright.config.ts` with no usable server/port under plain Playwright, breaking that portability guarantee. Baking concrete values keeps the config self-contained: it is correct whether reactlens drives the run or not. A reactlens.config-field design (devServer fields the template reads) was also considered but rejected for greenfield: it couples `playwright.config.ts` to a reactlens import and adds a config surface, where literal interpolation is the smaller change that closes the gap.

**Consequences:**

- The **Scaffold** is now a *materialized, stack-interpolated* artifact, genuinely distinct from the source-side templates inside the reactlens package — this is the distinction CONTEXT.md draws between "Scaffold" and "templates".
- Interpolated values can go stale if the user later changes their dev port or package manager. This is acceptable because re-`init` is idempotent and overwrites the Scaffold without prompting: the recovery path is `reactlens init`, not a manual edit.
- `detectStack` must grow to surface what the interpolation needs (notably the package manager, which today lives in `init`'s `detectPackageManager`, and the dev command). The data already exists; it was simply never wired into output.
- The greenfield-first scope holds: `init` interpolates and writes; it does not attempt to merge into a pre-existing user `playwright.config.ts`. Brownfield adoption is explicitly out of scope for this decision.
- Trade-off acknowledged: a project whose dev server cannot be expressed as `<pm> run dev` on the detected port (custom scripts, monorepo workspaces, non-standard ports behind a proxy) still needs the env-var escape hatch or a manual edit. The interpolation targets the common case, not every case.
