# `page.route` over MSW for provoking backend-driven component states

Status: supersedes the MSW rationale in CLAUDE.md §5 (tech stack).

CLAUDE.md §5 locked `msw` as a required dependency, on the rationale that "our generated tests need to mock APIs to provoke loading/error states" and that depending on a real backend "would make them flaky and useless". In practice the implementation drifted away from that decision without anyone recording it: the generation prompts (`generate-suite.md`, `generate-suite-component-object.md`) instruct the agent to provoke non-default backend responses with `page.route('**/api/...', ...)` plus a `?mocks=off` query param that supposedly disables "reactlens's MSW handlers". But **nothing implements that MSW layer**. There is no service worker, no `setupWorker`, no `worker.start()`, no `mockServiceWorker.js`, no `msw init public/`, and no app-side wiring that reads `?mocks=off`. `reactlens generate` does not even create the `src/mocks/handlers.ts` file that `reactlens.config.ts` points at. The `?mocks=off` convention is fiction; the only mechanism that actually provokes states today is `page.route`, which is Playwright-native and needs no service worker and no application wiring.

**Decision:** `page.route` is the canonical, out-of-the-box mechanism for provoking backend-driven component states. MSW is removed from the out-of-the-box path: `reactlens init` stops installing `msw`, the `?mocks=off` / "reactlens's MSW handlers" language leaves the generation prompts, the `reactlens.config.ts` `msw.handlers` field and the config schema entry are removed, and the `VISUAL_STATES` catalog emits `page.route` recipes (`mswRecipe` → a route-override recipe) instead of MSW handler strings. This supersedes the MSW rationale in §5.

**Why.** Completing the MSW story to match the prompts' assumption — a default in-app mock layer the app renders against, toggled by `?mocks=off` — would require injecting `setupWorker(...).start()` into the user's application entry point (`main.tsx`). That is a **user-owned** file, and our setup contract (CONTEXT.md / the init decisions) is that **Init never touches user-owned files** — it only writes the reactlens-owned **Scaffold**. So the MSW-default-layer design is in direct tension with the Scaffold/user-owned boundary, and it would also change the user's own dev-time behaviour. `page.route` sidesteps all of this: it is per-test, lives entirely inside the spec (reactlens-owned territory), requires zero app wiring, and intercepts regardless of whether the app has any mocking of its own. For an out-of-the-box tool, the mechanism that needs no foothold in the user's app wins.

**Consequences:**

- CLAUDE.md §5 is corrected in the same change: the tech-stack table row and the "Key new dependencies and why" paragraph for `msw` are updated to reflect that `page.route` is the state-provocation mechanism and MSW is not a runtime dependency of the out-of-the-box path.
- One fewer dependency installed into every user project; one fewer thing that can be misconfigured.
- `state-machine.ts` (`mswForState`) and the `VISUAL_STATES` catalog change shape: per-state data carries a `page.route` recipe instead of an MSW handler. The visual-state set itself (the moat-relevant enumeration) is unchanged — only the mocking encoding changes.
- The "app renders fully mocked by default, with a real-backend escape hatch" capability is explicitly **out of scope** for the out-of-the-box path. If it returns, it returns as an opt-in feature that the user knowingly wires into their own app entry — not something `init` injects.
- Trade-off acknowledged: `page.route` mocks at the network boundary per test, so a state that depends on the app booting against a mock layer *before* the first navigation (e.g. mocking that must be live during module-eval/bootstrap) is harder to express with `page.route` alone than with an always-on in-app worker. This is judged rare enough not to justify owning an app-entry injection.
