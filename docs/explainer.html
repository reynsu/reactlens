Built for Tabs

We're shipping Tabs faster than our tests can verify it.

Three engineers ship Tabs. One owns the web frontend. The way Tabs is tested today — pixel-based, manual triage, hours of "is this real or a flake?" — doesn't scale with the pace the product is moving. This closes that gap.

01 — The problem we have, specifically

Testing on a six-person team only works if it does most of the work itself.

At a bigger company, a flaky test goes to a QA engineer. On Tabs, it falls on whoever owns the frontend — every time. The triage isn't free: an afternoon spent reproducing a flake is an afternoon not spent shipping features. Multiply that across the year, and a meaningful chunk of frontend capacity goes to work nobody wanted.

The reason is structural. Every testing tool in use today (and every AI testing tool being marketed at startups right now) sees the rendered page. Pixels. It cannot see the components those pixels came from, the state that drove them, or the commit that changed yesterday's correct behavior into today's broken one. So when something looks off, no answer arrives — just a screenshot to squint at. That work falls back on the frontend, every time.

What our tests see today

A picture of the Tabs UI.

When the picture changes, we get an alert. Whether it's a real bug or a flake or someone moved a button by 2px is a manual judgment, every single time.

What reactlens sees

The Tabs UI, the React components that produced it, and what changed in the codebase since yesterday.

When something looks off, the diagnosis comes with the evidence already attached. No squinting.

02 — What it does

It gives our tooling what an engineer would tell it, if there were time to spare.

reactlens captures, for every test run against Tabs, the full structure of the app as it executes — every component, every state, every value, every change since the last run. That data is fed to Claude. The result is the first testing layer that sees Tabs the way an engineer reading the code sees it.

It isn't a smarter AI. It's the pipe that lets the AI already in use do its job against Tabs correctly.

The value isn't the AI itself — it's the data we give it about Tabs. Nobody else has that data, because nobody else has Tabs.
03 — What changes for Tabs

Three things stop costing us what they cost today.

01

Failure triage goes from hours to seconds.

Every failed test on Tabs comes back with a verdict — broken code, stale test, or noise — with the props, state, and recent commits attached as evidence. Anyone on the team can verify the call in a glance instead of running the suite five times.

02

Tests stop breaking on every UI change.

The tests we generate are anchored to Tabs' component structure, not its appearance. We can redesign a screen, refactor a component, swap a styling library — the tests stay green because they're testing what the components do, not what they look like.

03

Quality becomes a property of every run, not a sprint of its own.

Accessibility checks, regression detection, behavioral drift — these run on every test, every time, automatically. Quality work stops being something we have to schedule and starts being something the system enforces.

04 — Why this matters at our size

We are six. The testing layer has to punch above its weight.

A bigger team can afford to dedicate people to test infrastructure. We can't. Whatever we adopt has to do the work that elsewhere would be done by a QA engineer, a release engineer, and an accessibility consultant — on top of doing the actual testing.
