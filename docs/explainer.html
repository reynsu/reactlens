The first E2E testing tool that understands your React code, not just your DOM.

Every other E2E tool — Playwright, Cypress, QA Wolf, Octomind, Mabl — treats your app as a black box. They see HTML and pixels. They never see what you see: a tree of <Component>s with props, state, hooks, and a known relationship to your source files. That's the whole moat.

The problem

When a test fails, you have to answer two expensive questions.

  1. Is this a test bug or a real bug? — this is where 90% of triage time goes.
  2. If it's a real bug, where exactly in my code?

Existing tools can't really help with either. They show you a stack trace and a screenshot. They guess from the DOM because that's all they see. The DOM doesn't tell you which prop was wrong, which hook returned bad data, or which commit just touched the relevant file.

The trick

A small probe injected into your app captures the React tree at every render.

reactlens bundles a ~19 KB IIFE that the Playwright fixture injects into every page before navigation. It uses bippy — a tiny library that wraps React's internal fiber access in a version-safe way — to subscribe to fiber commits. On every render it walks the tree, sanitizes props and hooks, attributes every data-testid to its owning component, and ships the result over WebSocket to the dashboard.

That's one data source. There are two more, captured by the same fixture at end-of-test:

  • The full accessibility tree via Chrome DevTools Protocol (since Playwright dropped its a11y API in 1.45+).
  • One event per axe-core violation found against the rendered DOM.

All three streams plus per-step CDP screencast frames get persisted under .reactlens/runs/<runId>/. You can replay any past test offline, scrub through it with a slider in the dashboard, or diff it against another run — no need to re-run Playwright.

How Claude fits in

Claude shows up in two places. They are very different jobs.

reactlens uses the @anthropic-ai/claude-agent-sdk with Sonnet 4.x by default. Claude is asked to do exactly two things — write tests and diagnose failures — and in both cases the prompt is grounded in evidence that no other testing tool can give a model.

Moment 1 — reactlens generate

Writing test specs from your source, not your screenshots

Before any LLM call, reactlens parses the component with ts-morph and enumerates every visual state the component can be in. For a typical <CheckoutPage> that means: idle, submitting, declined, network-error, validation-error.

1AST parsets-morph reads the component
2Enumerate statesuseState / useQuery / conditional JSX
3Prompt Claude"cover each state explicitly"
4Claude writes specsPOM + Playwright + MSW handlers
5Verifytsc --noEmit + contract.md
What Claude receives
  • The component source file
  • The enumerated VisualState[] from the AST analyzer
  • The list of API endpoints referenced inside the component (so it can mock them with MSW)
  • The project's stack signature (Vite / Next / TanStack) so route imports are right

Claude has Read, Write, and Bash tools and writes the e2e/pages/ and e2e/specs/ files directly. reactlens then runs tsc --noEmit to verify the output type-checks, and writes a <Component>.contract.md next to each spec so you can read what the analyzer thought the states were before approving anything.

Moment 2 — reactlens run (on failure)

Diagnosing a failing test with the actual React tree at the moment of failure

When a test fails, reactlens does not hand Claude a stack trace and a screenshot. It hands Claude the component tree snapshot at the moment of failure — every prop, every hook value, every source location — plus the component source, the spec source, and git blame for both.

What Claude receives
  • The component source file
  • The spec source file
  • The last component:snapshot captured before the failure (props + hooks + tree)
  • The Playwright error message
  • Git log for both files (who touched them last, and when)

The output is a strictly-typed Diagnosis (validated with Zod — if the model returns bad JSON, reactlens retries). Here's a real example:

real-bug confidence: high checkout.spec.ts › submits valid CVV
Root cause
CVV validation now requires min(3) digits; the spec submits "12", which the form correctly rejects.
Evidence
  • Snapshot shows <CvvInput> value="12" and cvvValid: false
  • SubmitButton has disabled: true at the failing step
  • Component last changed by alice@ in commit 4f3a91b (yesterday): "tighten CVV schema to min(3)"
  • Spec last changed 3 weeks ago — predates the schema tightening
Suggested fix
Update the spec to submit a valid 3-digit CVV.
e2e/specs/checkout.spec.ts
- await page.getByTestId('cvv-input').fill('12');
+ await page.getByTestId('cvv-input').fill('123');

The patch is never auto-applied. The dashboard surfaces it with a "copy" button. You review the diff and apply by hand. This is a hard rule, written into the project's contributor instructions.

An optional third path: --use-claude-code routes through your local claude CLI instead of the API, billing against your Claude Max subscription. Local development only — Anthropic's ToS prohibits this for distributed tools.

How the diagnosis stays honest

An LLM with calibrated confidence is qualitatively different from "AI suggests a fix".

Every release of reactlens runs the diagnosis agent against a hand-labeled eval set in tests/diagnostic-eval/cases/. Sixteen failure scenarios — some are real bugs (validation tightened, prop renamed, async race), some are test bugs (stale selector, copied spec not updated, missing MSW handler), some are flaky (state leaked between tests via localStorage, IndexedDB, MSW handler residual), some are env issues.

100%
Accuracy on the 16-case eval · current baseline

If a release regresses the eval accuracy, it doesn't ship. The eval gate runs in CI on every PR and aborts the release pipeline when accuracy < 80% or falseConfidenceRate > 5%. When a real-world failure stumps the diagnosis agent, the labeled case gets added to the eval set so future regressions catch it.

The four test-bug subtypes and five state-leak surfaces are all covered. The disambiguation rule that distinguishes "spec drift" from "code regression" generalizes — a brand-new case (case-016 from a recent ToS-checkbox bug) classified test-bug / high first try.

What you do

Install once. Two commands cover daily use.

# one-time setup
pnpm add -D reactlens
npx reactlens init           # detects your stack, copies templates, installs Playwright + MSW

# daily loop
npx reactlens generate       # AI writes/updates specs from your source
npx reactlens run --watch    # dashboard at localhost:7777, re-runs on file changes

# after the fact
npx reactlens diff <runA> <runB>     # semantic diff (component tree + a11y), not pixels
npx reactlens analyze report.json     # diagnose a CI JSON report

Supported stacks: Vite + React Router (React 18 and 19), Next.js 14 App Router, and TanStack Router. All four have full fixtures and end-to-end integration coverage.

What you don't have to worry about

Local-first guarantees, written down so they don't drift.

✓
No cloud sync, no hosted dashboard Everything runs on your machine. The dashboard server binds to localhost:7777.
✓
No telemetry, no phone-home Zero. The Anthropic API is the only network call, and only when you invoke generate or run with diagnosis on.
✓
Patches are never auto-applied The diagnosis agent proposes. You review and apply by hand. Encoded as a project-level rule.
✓
Cost is hard-capped --max-cost <usd> aborts at the next message boundary once the cap is hit. Every call's token usage is tracked.
✓
Run artifacts auto-gitignored The persistor drops a * .gitignore into .reactlens/ on first run. Your repo doesn't accidentally commit runs.
✓
Calibrated, not asserted, confidence "High confidence" means the model has been verified correct at high frequency on a labeled eval set. Releases regressing accuracy don't ship.

Why this is different

The 90% of value isn't the AI — it's the data the AI gets to see.

Most "AI testing tools" sold today take a screenshot, hand it to an LLM, and ask it to guess selectors. That fails predictably because the LLM has no idea which component rendered what, can't distinguish "the code changed" from "the test got stale" when something breaks, and generates brittle selectors that imitate whatever Tailwind soup it saw.

TL;DR

One capture layer, two Claude touchpoints.

What the capture layer gets you (local, free)
  • React component tree per render via probe + bippy
  • Accessibility tree per test via CDP
  • axe-core violations per test
  • CDP screencast frames per step
  • Everything persisted to .reactlens/runs/<id>/ for offline replay
  • Behavior contracts (.contract.md) alongside generated specs
  • Semantic diff (component + a11y) between any two runs
What Claude does (API or local CLI)
  • Writes Playwright specs + POMs covering every visual state the AST identified
  • Diagnoses each failure with classification + confidence + evidence + suggested patch
  • Calibrated against a 16-case eval set on every release
  • Never auto-applies anything
  • Cost-capped per command

People will call this "an AI testing tool" but the AI is the smaller half. The bigger half is giving the model information no other testing tool can give it: your source via AST, your component tree via probe, your git history. That's the moat.
