reactlens / nota de arquitectura Agent layer · versión corta

Decisión técnica

Una capa de agentes sin casarnos con un proveedor.

reactlens necesita modelos para generar tests, diagnosticar fallos y explicar causas. La pregunta no es si podemos soportar Claude, OpenAI, Gemini o modelos locales. Podemos. La pregunta es cuánto coste permanente aceptamos por esa flexibilidad.

Veredicto

Abstraer ahora. Añadir backends después. Mantener Claude como backend principal hasta que haya demanda real o benchmarks que justifiquen otro proveedor.

Problema Comparación Arquitecturas Costes Decisión

El problema

Hoy la capa de agentes de reactlens está orientada a Claude. Eso es práctico: los prompts, las evaluaciones y el flujo de herramientas ya están afinados ahí. Pero deja cuatro riesgos: dependencia de precio, cambios de API, preferencias del usuario y restricciones de privacidad.

Necesario

Un contrato común

Una interfaz propia para streaming, herramientas, JSON estructurado y uso de tokens.

Peligroso

Multiproveedor completo

Cada backend exige prompts, evals, límites, costes y mantenimiento propios.

Mejor ahora

Claude por defecto

Menos variabilidad mientras la herramienta todavía está buscando precisión diagnóstica.

Arquitecturas posibles

Recomendada

1. Contrato común, un backend

Crear AgentBackend, mover Claude detrás del contrato y dejar la extensión lista.

  • Pros: barato, reduce lock-in, no multiplica evals.
  • Contras: el usuario aún no puede cambiar de proveedor.
  • Arquitectura: reactlens → AgentBackend → Claude.
Solo con demanda

2. Claude + OpenAI experimental

Añadir OpenAI detrás de una flag y correr los mismos evals con baseline separado.

  • Pros: valida la abstracción, opción real para usuarios.
  • Contras: prompts y confianza dejan de ser universales.
  • Arquitectura: reactlens → router simple → Claude/OpenAI.
No ahora

3. Multiproveedor completo

Prompts, evals, costes, límites y routing por tarea para cada backend.

  • Pros: máxima flexibilidad, buen mensaje comercial.
  • Contras: matriz permanente de mantenimiento.
  • Arquitectura: reactlens → policy router → N backends + eval gates.

El punto clave: la abstracción debe normalizar eventos, herramientas, JSON y coste. No debe intentar hacer que todos los modelos “piensen igual”. Eso se mide con evals, no se arregla con tipos.

Costes reales

Costes técnicos

  • Interfaz común: 1-2 días.
  • OpenAI experimental: ~1 semana + baseline de eval.
  • Gemini: ~1-2 semanas por ajuste de tool use y streaming.
  • Local/self-hosted: integración fácil, calidad difícil.
  • Multiproveedor serio: 1-2 meses iniciales + mantenimiento continuo.

Costes de producto

  • Confianza: cada backend necesita calibrar high | medium | low.
  • Prompts: un prompt universal baja calidad; prompts por backend duplican trabajo.
  • Soporte: cada proveedor añade bugs que parecen de reactlens.
  • CI: cada backend caro vuelve lento o costoso el release gate.
  • UX: demasiadas opciones confunden antes de aportar valor.

Configuración por defecto: subscription antes que API

Decisión de policy independiente de qué backends soporta reactlens. Aplica al backend Claude que ya está integrado, y a cualquier backend futuro con la misma dualidad subscription/API.

El pitfall. Si ANTHROPIC_API_KEY está presente en el entorno, Claude Code factura contra la API en vez de contra la Pro/Max subscription — aunque el usuario haya iniciado sesión en Claude Code y quiera usar el plan que ya paga. Anthropic lo documenta. La consecuencia para reactlens es facturación accidental: una env var olvidada en el shell del developer cuesta dinero real al final del mes.

Orden de precedencia

La auto-detección debería preferir subscription siempre que esté disponible. Solo caer a API key cuando no hay otra opción.

Prioridad Fuente Cuándo se elige
1 --agent claude-cli o REACTLENS_AGENT_BACKEND=claude-cli Override explícito del usuario. Siempre gana.
2 Claude Code subscription detectada (claude binary en $PATH + sesión activa) Default recomendado. Usa la suscripción del developer; cero coste API para el proyecto.
3 Otra CLI con subscription (codex, gemini) Si Claude Code no está pero hay otro CLI autenticado.
4 ANTHROPIC_API_KEY en entorno Solo como último recurso. Si las opciones 2 y 3 fallaron.
5 Otra API key (OpenAI, Google) Cuando hay backend correspondiente implementado y autenticado.

Mitigación del pitfall

  • Detectar la colisión. Si Claude Code está disponible Y ANTHROPIC_API_KEY está en el entorno, reactlens elige la subscription pero loguea un aviso explícito: "Detected ANTHROPIC_API_KEY but using Claude Code subscription. Set REACTLENS_FORCE_API=1 to override."
  • Override explícito y consciente. Si el usuario realmente quiere facturar contra API (por ejemplo en CI sin subscription disponible), el override debe ser una variable separada, no la presencia accidental de la key.
  • Documentar la jerarquía. README, --help, y reactlens init deben dejar clara la precedencia. La sorpresa más cara es la que no se vio venir.
Resumen: subscription es default; API es fallback consciente; la presencia de una env var nunca debe cambiar billing sin avisar.

Decisión recomendada

Implementar una capa AgentBackend ahora, pero seguir enviando solo Claude. Es la mejor relación coste/beneficio: reduce el acoplamiento, prepara una salida si cambia el mercado y no obliga al equipo a mantener cinco caminos frágiles.
