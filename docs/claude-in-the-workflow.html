CLAUDE × REACTLENS Engineering doc · ~6-minute read
Integration architecture · current tradeoffs · what to improve next

How Claude is plugged into reactlens, and where the implementation has room to grow.

reactlens uses Claude in two distinct pipelines — test generation and failure diagnosis — through a thin AgentRunner abstraction that backs onto either the Anthropic SDK or the local claude CLI. This document walks through which Claude surfaces are wired up, how they're orchestrated, what's working well, where the current design leaves performance and reliability on the table, and the concrete upgrades worth doing next.

01 — The four Claude surfaces, and which ones reactlens touches

One SDK, one CLI, one HTTP API, one subscription. Three are wired in; one is not.

The split between SDK and CLI exists for one reason: cost. The SDK is the only path reactlens can ship to other users. claude -p is faster and cheaper for the developer working on reactlens itself, because it bills against the Max subscription you're already paying for.

02 — The integration architecture

A thin abstraction, two backends, one cost-tracking decorator. Everything else is prompts and parsers.

Every Claude-driven command (generate, run's diagnosis path, analyze, regen) follows the same shape. The wiring lives in src/agent/:

CLI command (e.g. reactlens run)   ↓ pickAgentRunner({ useClaudeCode? })   ├─ SDKRunner — wraps query() from agent-sdk   └─ CLIRunner — spawns claude -p, parses stdout   ↓ withCostTracking(runner, costTracker) // decorator   ↓ diagnose(agent, failure) | generateTests(agent, ...)   ↓ Zod schema validates JSON output · retries on bad shape   ↓ Bus events: diagnosis:chunk (stream) → diagnosis:end (final)

The runner abstraction

AgentRunner is the seam. It exposes one method — an async generator of message events — that both backends implement. The SDK runner forwards events from query() as-is; the CLI runner reads claude -p's stdout line by line and synthesizes equivalent events. Call sites don't know which backend they're on. 

// src/agent/select.ts
export async function pickAgentRunner(opts: {
  commandName: 'generate' | 'run' | 'analyze' | 'regen';
  useClaudeCode?: boolean;
}): Promise<AgentRunner> {
  const useCLI = opts.useClaudeCode === true
    || process.env.REACTLENS_USE_CLAUDE_CODE === '1';
  return useCLI ? new CLIRunner() : new SDKRunner();
}

The cost-tracking decorator

withCostTracking wraps either runner. It listens for the SDK's result events (which carry per-message usage: input tokens, output tokens, cache reads, cache writes) and accumulates dollar cost via a model-pricing table. When the running total crosses --max-cost, the wrapper throws AGENT_COST_EXCEEDED at the next message boundary. Same shape for the CLI runner, but with token counts approximated from response length when not returned.

What flows through the pipeline

Prompts live as Markdown templates in src/{analyzer,generator}/prompts/*.md with placeholder substitution. Output is parsed with a Zod schema (Diagnosis for failure analysis; nothing structured for generation — that path just writes files). On bad JSON, the diagnose path retries once with an explicit "your last reply was not valid JSON" follow-up.

03 — What Claude is doing at each pipeline point

Two flavors of agent call. Different tools, different output contracts.

A · reactlens generate

Multi-step agent loop with full tool access

InputComponentAnalysis + output paths + MSW config
ToolsRead, Write, Bash
Loopread source → write POM → write spec → tsc → fix
OutputfilesWritten: string[]
Schemanone (file side-effects only)

The model is a free-roaming agent. It can read any file, write any file, and run any command in the cwd. reactlens trusts the agent loop to converge — it only validates the output by running tsc --noEmit after.

B · reactlens run (diagnosis)

Single-shot streaming query with structured output

Inputfailure { testId, title, file, error, snapshot }
Toolsnone
Loopsingle query, streamed text chunks
OutputDiagnosis (Zod-validated)
Schemaclassification + confidence + evidence + patch?

Read-only call. The prompt carries every shred of context the model needs — component source, spec source, last component:snapshot, git context — and asks for a JSON object. Streaming chunks land on the bus as diagnosis:chunk events for live UI feedback.

analyze and regen are variants: analyze hits the diagnose path per failure in a Playwright JSON report; regen hashes component sources, then invokes the generate path only for ones whose hash changed.

04 — Pros and cons of the current implementation

Clean abstractions, calibrated outputs. Cost and prompt evolution are the weak spots.

What's working
  • AgentRunner abstraction is the right seam. SDK vs CLI swap doesn't touch call sites. Adding a third backend (custom HTTP, a different vendor) is a one-file change.
  • Zod-validated output + retry. Bad JSON doesn't crash the pipeline. The schema rejects garbage early, and the prompt retries with explicit feedback.
  • Cost cap, eval gate, calibration. --max-cost aborts at the next message boundary. The 16-case eval set enforces ≥80% overall accuracy + ≥95% on high-confidence diagnoses before any release.
  • Streaming feedback in the dashboard. diagnosis:chunk events flow live to the inspector, so the developer sees the model thinking, not a spinner.
  • Decorator pattern (withCostTracking). Composable. The cost tracker is one of N decorators the runner could be wrapped in next — retry, logging, rate limiting all fit the same shape.
  • Prompts are markdown, in tree, in git. Iterable. Reviewable in PRs. No external prompt-management service to coordinate.
Where the design leaves value on the table
  • No prompt caching. The diagnosis prompt has a large fixed prefix (component source + git context). Anthropic supports cache_control; we're not using it. Multi-failure runs re-tokenize the same context every call.
  • No model routing. Sonnet for everything. Trivial classifications (e.g. "is this output a real diagnosis or did the model refuse?") could run on Haiku for ~10× cheaper.
  • No few-shot from the eval set. The 16 hand-labeled cases sit unused at inference time. Including 2-3 as in-context demonstrations would likely push accuracy higher on edge cases.
  • Generic tools for generate. The agent has Read/Write/Bash — the default kit. Domain-specific tools (writeSpec, enumerateVisualStates) would shrink the surface for hallucination.
  • Tool failures don't feed back into the agent loop. If a Write produces broken TS, tsc fails after the loop, not inside it. The model never sees the error and can't recover.
  • Cost cap is coarse. Aborts only at message boundaries. A single long streaming response can overshoot the cap before the next check.
  • CLI runner is approximate. claude -p doesn't return structured usage counts by default. The CLIRunner estimates from output length, so the cost tracker's numbers under --use-claude-code are directional, not exact.
  • Hardcoded model selection. Model strings live in src/config/. Not env-overrideable per-command, which makes A/B comparing Sonnet vs Opus on the eval set a manual edit-and-rerun.

05 — Alternatives, in priority order

Cheapest, highest-leverage upgrades first. None of these are research projects.

01 · cheapest win

Prompt caching with Anthropic's cache_control

The diagnosis prompt's fixed prefix — component source, git context, schema definitions, prompt template — is identical across every failure in a single run. Marking that prefix with cache_control: { type: 'ephemeral' } cuts the input-token cost on subsequent calls within the cache TTL (~5 min) by roughly half. The SDK supports it directly; the change is a single decorator on the prompt.

Effort:one afternoon
02 · high-leverage

Model routing: Haiku for triage, Sonnet for diagnosis, Opus for low-confidence retries

Today every diagnose call goes to Sonnet. Two tiers of cheaper traffic are sitting unused. Pre-screen with Haiku (does this look like a flaky test, a real bug, or a test bug? one-line classification). If Sonnet's first-pass diagnosis comes back with confidence: low, retry on Opus before giving up. The router lives next to pickAgentRunner and decides per-call which model the runner targets.

Effort:a few days · needs eval-set re-baseline
03 · accuracy

Few-shot examples drawn from the eval set itself

16 hand-labeled failure cases sit in tests/diagnostic-eval/cases/. Sampling 2-3 of them (by category — one real-bug, one test-bug, one flaky) into the diagnosis prompt as in-context demonstrations would calibrate the model on the project's own conventions. Anthropic's prompt caching is the right home for these — they don't change between calls.

Effort:one day · iterate on which examples
04 · correctness

Domain-specific tools for the generate agent

Replace generic Read/Write/Bash with a tighter kit: readComponentSource(file), writeSpec({ name, states, fileContents }), writePOM({...}), runTypecheck(). Schemas on these tools shrink the surface for hallucination (the model can't invent invalid file paths or skip the structure we want) and let reactlens validate inputs at the tool boundary instead of discovering errors post-hoc with tsc.

Effort:a week · touches the generate prompt
05 · robustness

Tool failure feedback inside the agent loop

When a generated spec fails to typecheck today, the run ends and the engineer is left with broken output. The fix: catch the tsc output, surface it to the agent as a follow-up message ("your spec doesn't typecheck; here's the error; try again"), and give it one more iteration. The SDK's tool-use loop handles this natively — we just need the tools wired right and a max-iterations cap.

Effort:a few days
06 · observability

Persist every Claude call into the run's events.jsonl

Today the cost tracker accumulates a number; the prompt + completion themselves aren't stored. Logging each call as an event (input tokens, output tokens, prompt hash, model, latency, success/failure) into the run's persistence layer makes the diagnosis pipeline debuggable after the fact — "why did the model say X here" stops being a re-run-it exercise.

Effort:a couple of days · mostly plumbing
07 · further out

A/B prompt evaluation against the eval set as a script

Today prompt iteration is "edit the markdown, run the eval, eyeball the diff". A small harness that takes two prompt variants and runs both against all 16 eval cases, reporting per-class accuracy + confidence calibration, would make prompt evolution systematic. Lives next to tests/diagnostic-eval/; consumes the same data the release gate already does.

Effort:half a day · pure scripting
08 · nice to have

Structured cost reporting from claude -p

Currently the CLIRunner approximates tokens from output length. claude -p supports a JSON output mode that includes per-message usage. Switching the CLI parser to consume that mode makes --max-cost exact under --use-claude-code instead of directional.

Effort:half a day
06 — The shortlist if budget is one engineer-week

Cache the prompt, route the model, log the calls. In that order.

Prompt caching is the highest-leverage and lowest-risk change — pure cost reduction, no accuracy tradeoff. Model routing comes next, conditional on re-baselining the eval gate after the change (Haiku might drop accuracy on the triage step; the eval will catch it). Persisting every Claude call into the run JSONL is third — it's the foundation for every future diagnostic step we'll want to take on this pipeline. The other five entries in §05 are real but can wait.

Everything in §05 is a delta from a working baseline. The current implementation already ships diagnoses at 100% accuracy on the 16-case eval and generates passing specs from AST input. The upgrades aren't about fixing what's broken — they're about how much headroom is left in the same architecture.
